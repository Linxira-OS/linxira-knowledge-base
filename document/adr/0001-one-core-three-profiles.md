# ADR 0001：一个内核，三档 profile

- **状态**：Accepted
- **日期**：2026-11-08

## 背景

v1 是一套企业版架构：外部数据库、独立向量服务、SSO、多租户。它解决的是企业客户的问题，但新要求是"个人可用、企业可用"。

两种直觉做法都不能接受：

1. 另做一套轻量版给个人。结果是两份代码、两套检索语义、两条引用格式。同一个召回缺陷要修两遍；更糟的是数据从个人档升级到企业档时没有迁移路径，只能重新导入，历史引用全部失效。
2. 只保留企业版，用开关裁剪功能。个人用户依然要装 Postgres、配 SSO 才能启动，运维成本没有下降，只是把复杂度藏进了配置项。

真正需要共享的是语义，而不是部署形态：摄入与 doc_id 派生、召回通道组合与多通道融合、打分、Answer 契约、降级语义。真正需要替换的是基础设施：存储与索引、身份、策略、算力。

## 决策

**单一内核 + 三档 profile（solo / team / enterprise）。档位 = 配置 + 适配器选择，不 fork 代码。**

- 内核拥有且只拥有一份实现：摄入与解析、doc_id 派生、检索管线（召回、融合、TopN 打分）、Answer 生产、degraded 上报、治理过滤的调用位置。
- 档位通过端口（port）绑定不同适配器：存储与索引后端、embedding 提供方、身份提供方、策略引擎、可选能力（LLM、图谱、多模态）。profile 是一个声明式配置包，不是代码分支。
- 领域逻辑中不得出现 `if tier == ...` 形式的分支。档位只影响装配（wiring）与参数。
- 最低档是内核的设计约束：solo 必须零外部依赖——SQLite FTS5 BM25 即可独立成路；向量（本地 ONNX 嵌入 + sqlite-vec）与 LLM 都是可选升级；无 LLM 时以抽取式回答兜底。任何需要外部服务才能在 solo 成立的设计都被否决。

## 备选方案与为何不选

| 方案 | 否决理由 |
| --- | --- |
| solo 与企业各自独立代码库 | 双份维护与语义漂移；跨档迁移需要重新实现摄入与引用，doc_id 无法稳定（见 ADR 0003） |
| 只做企业版，用功能开关裁剪 | 个人档的启动门槛未降低；开关组合爆炸后，测试矩阵无法覆盖真实运行形态 |
| solo 只做文件搜索，企业另建系统 | Answer 契约与评测无法统一，同一问题在两档得到不可比的回答（见 ADR 0005） |
| 用插件/脚本让用户自己组装 | 默认配置会碎片化，治理与降级语义无人保证；个人用户没有能力承担装配工作 |

## 后果

**正面**

- 一套语义：检索、引用、降级、治理过滤只实现一次，缺陷修复与评测增益全档受益。
- 渐进升级：solo → team → enterprise 是换 profile 与适配器，数据不需要重写导入。
- 治理能力在低档即被调用与测试，不会在企业交付前才第一次跑通。

**负面**

- 抽象税：内核必须面向最低档设计，端口层与适配器装配是额外结构。
- 企业特性不能假设基础设施必然存在（例如不能假定有外部队列或缓存），部分能力必须以可选适配器形式提供。
- 端口一旦定义就成为跨档契约，修改成本高于单档系统内部的接口。

**需要监控的信号**

- 领域代码中出现档位条件分支的数量（目标为 0）。
- 适配器接口数量与单次新增档位的装配改动量；接口持续膨胀说明抽象泄漏。
- solo 启动时的外部依赖数与网络调用数（目标为 0）；出现即违反最低档约束。
- 跨档行为差异用例数：同一数据集在三档下 Recall / 引用可回跳率的差异应可解释， unexplained 差异应归零。
