# ADR 0003：文件是事实源，索引是派生

- **状态**：Accepted
- **日期**：2026-11-08

## 背景

知识库有两种常见的事实源选择：以文件（Markdown、PDF、附件）为准，或以数据库/索引为准。后者在写入路径上更"整齐"，但带来三个问题：

- **不可恢复**：索引损坏、模型升级、分词器变更都会让派生数据失效；若索引是唯一副本，重建等于重新收集资料。
- **不可审查**：个人场景里，git 与目录备份已经是最可靠的版本控制；企业场景里，原文是审计与合规的凭据，向量只是它的投影。
- **引用断裂**：Answer 必须能回跳到原文（ADR 0005）。索引里没有权威位置，引用就只能指向索引条目，无法核对。

同时，v1 的经验是**双源**（文件 + 副源，例如协作平台或业务库）在 enterprise 是必须的：组织内的事实往往先出现在协作系统里，文件只是导出物。但这套双源机制对个人用户是纯负担。

## 决策

**文件是事实源（source of truth），索引是派生（derived）且可全量重建；doc_id 由内容指纹 + 逻辑路径派生，跨档迁移保持稳定。**

- solo 档事实源 = Markdown + 附件；双源转写（文件与副源之间同步、互校）可选，不开启时不存在副源。
- enterprise 档双源必选，并保留 v1 的"双源可核对"取舍：任一来源的差异必须能被发现，而不是静默以某一侧为准。
- 索引（分块、向量、全文倒排、治理字段的索引副本）可在不读取任何外部状态的情况下由事实源重建。删除索引不丢信息。
- doc_id 派生规则：内容指纹（content fingerprint）+ 逻辑路径（logical path）。同一份内容放在同一逻辑路径下，在任何档位、任何重建之后得到同一 doc_id；因此引用、ACL 绑定、评测标注不因迁移而失效。
- 写入顺序固定为"源文件先落盘、索引后更新"，索引更新幂等；崩溃后以重建或重放收敛，不做补偿性写回。

## 备选方案与为何不选

| 方案 | 否决理由 |
| --- | --- |
| 以数据库或向量库为事实源 | 单点不可恢复；无法用目录备份与 git 审查；个人档被迫引入外部服务，违反 ADR 0001 的最低档约束 |
| 以索引为主、文件为导出物 | 迁移与审计都需要原始文本；模型升级后无法重新生成等价索引 |
| doc_id 用自增主键或随机 UUID | 重建或迁移后 id 漂移，引用、评测标注、ACL 绑定全部失效；跨档升级必须重新导入 |
| doc_id 只用内容指纹 | 相同内容出现在多个路径时无法区分（同文多空间、模板文件），治理归属会互相覆盖 |
| doc_id 只用逻辑路径 | 内容被替换后仍沿用旧 id，版本与引用指向错误内容，历史不可追溯 |

## 后果

**正面**

- 备份策略退化为"备份目录"；索引损坏、embedding 模型更换、分片调整都可以重建而非迁移数据。
- 引用可回跳有据可依：引用由 doc_id + 位置构成，位置指向源文件的段落或页码。
- 双源可选让 solo 保持零外部依赖，同时不排除企业档的核对需求。

**负面**

- 重建成本高：全量 embedding 与全文索引重建是重计算任务，需要增量与并行的设计。
- 内容指纹对格式敏感，换行或排版变化会产生新 doc_id，历史引用指向旧版本；需要与 `version`（ADR 0002）配合表达"同一文档的演进"。
- 逻辑路径变更（重命名、移动）等价于新 doc_id，需要在迁移工具中显式处理，不能隐式跟随。
- 双源开启时存在一致性窗口：文件已更新而副源未同步（或反之），必须有核对任务而非假设一致。

**需要监控的信号**

- 全量重建的成功率与耗时；重建后 doc_id 集合与重建前的一致性（差异应为 0）。
- 同一内容指纹对应多个逻辑路径的数量（同文多副本），以及同一逻辑路径下 doc_id 频繁变更的次数。
- 孤儿索引条目数（源文件已不存在）与缺失索引条目数（源文件存在但未入索引），两者目标均为 0。
- 双源开启时的差异条目数与差异存续时长；长时间未收敛说明同步或核对失效。
- 写入顺序违规次数（索引先于文件落盘），目标为 0。
