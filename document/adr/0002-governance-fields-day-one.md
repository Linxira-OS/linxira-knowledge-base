# ADR 0002：治理字段第一天就在 schema 中

- **状态**：Accepted
- **日期**：2026-11-08

## 背景

"个人档不需要权限，等企业档再加"是常见做法，但它把三类成本推迟到最不该付的时候：

- **数据回填**：历史文档没有 tenant_id / space_id，加字段时必须为存量数据选定归属，这通常需要人工确认，且无法回滚。
- **查询改造**：召回路径原本不带过滤条件，补 ACL 时要在每个召回分支插入过滤，并重新验证 TopN 语义；漏掉一条分支就是越权泄漏。
- **语义分叉**：个人档的 schema 与企业档不同，升级路径变成 schema 迁移 + 数据搬迁，而不是切换配置。

治理字段的另一个作用是**让"为什么这条结果被返回"可回答**。有效期（valid_from / valid_to）与版本（version）不是权限，而是可解释性：一条过期的制度文档被召回，和一条无权限文档被召回，是两类不同的错误。

## 决策

**七个治理字段（含 `superseded_by`）从基础 schema 起即存在，并在所有档位写入：`tenant_id`、`space_id`、`ACL`、`valid_from`、`valid_to`、`version`、`superseded_by`。**

- solo 档不省略字段，而是用固定值填充：单租户、单空间、allow-all（全放行）ACL；有效期按文档自身的时间属性写入，未知时使用开区间而不是留空。
- 召回路径始终携带治理过滤，即使过滤条件在 solo 下恒真。过滤发生在召回阶段，不是取回结果后的后置剔除（保留 v1 的有效取舍）；融合与重排后再做一次轻量 ACL 复核作为纵深防御，它不替代召回期过滤。
- 字段语义跨档一致：`valid_from` / `valid_to` 表示事实有效期，`version` 表示记录版本，`ACL` 表示可读取主体集合（solo 为全主体），`superseded_by` 表示被新 `doc_id` 替代（内容变化或跨文档替代），旧记录保留以便历史引用解析。
- 身份与 ACL 属于安全能力，不参与降级放行：身份不可用时拒绝请求而非放行（见 ADR 0004）。

## 备选方案与为何不选

| 方案 | 否决理由 |
| --- | --- |
| solo 用精简 schema，team 起再补字段 | 回填与查询改造集中在升级时刻，且存量数据归属需要人工判断；双 schema 意味着双写入契约、双查询路径 |
| 只在 enterprise 强制治理 | 召回管线会分叉，违反 ADR 0001；低档从未测试过过滤路径，企业版首次上线即承担全部风险 |
| 用视图或默认值在读取时补齐 | 写入契约被放宽，缺失值在升级时才暴露；且过滤仍不在召回查询里，无法保证截断顺序正确 |
| 把 ACL 只放在应用层结果过滤 | 无权限文档会占用 TopN 名额，既泄漏存在性也降低有效召回；与"召回期过滤"的既有取舍冲突 |

## 后果

**正面**

- 升级路径只改配置与后端，不改 schema、不改查询；跨档迁移时治理语义已经存在。
- 治理过滤在所有档位被执行，低档即可回归测试，企业档上线前已积累用例。
- 引用与结果可解释：有效期、版本、空间归属随结果一起返回。

**负面**

- solo 的每条记录带冗余字段，存储与心智成本增加；allow-all 容易被误读为"无需鉴权"，需要在策略层显式表达而非隐式缺省。
- 摄入时必须确定有效期；无法确定时以开区间表达，不能靠 NULL 语义猜测。
- ACL 在召回期过滤要求索引结构支持过滤，限制了纯向量索引的自由度（需与候选生成方式联合设计）。

**需要监控的信号**

- 治理字段空值率（目标为 0，solo 也不例外）。
- 召回查询中缺失治理过滤的次数；可用查询计划核对过滤是否先于 TopN 截断。
- 被后置剔除（而非召回期过滤）的结果数量，目标为 0。
- ACL 变更到生效之间的检索次数；缓存必须按权限版本失效，不能有不可观测的窗口。
- 有效期异常分布：`valid_from > valid_to` 的写入应被拒绝并计数。
