02 / CONFIG

配置项矩阵what each profile may change

锁定 = 启动校验或归一化拒绝，不是 UI 不能改。所有配置都在启动时读取；没有热更新。`features.*` 是覆盖层，默认值由 deployment.mode 决定；改 profile / backend 属于迁移，不是运行时切换。

Normalize

solo 强制 tenant_id=t_local、default_space=s_default，关闭组创建，但保留自助笔记本（space，受 spaces.max_per_user 约束）。team / enterprise 只在值仍等于默认值时收紧 limits，不覆盖显式配置。

Validate

profile 与 backend 不匹配（team / enterprise + sqlite）、solo 开 billing、enterprise 关 audit、enterprise_external 缺 signup/billing/multi_tenant/public_api、非回环 + auth.mode=none、PG 无 URL——都直接拒绝启动。

Runtime

模型 provider=none 不是配置错误：对应通道被裁剪，写入 degraded[]，其他通道继续。功能 flag 也不都等于实现；只有 billing / connectors / audit / quotas 有运行时门禁；audit 只门禁查询 API，quotas 只门禁写接口 †4。

03 / RETRIEVAL

检索链路与加权keyword first, optional channels, rank fusion

BM25 是基线，dense 与 event-entity 是可选通道。RRF 只比较名次，不比较不同通道的原始分数；judge 只重排已召回候选，不改变候选集。通道缺失写 degraded[]；hybrid 未配置 judge 是例外——不写 degraded，配置后失败才写 decision_unavailable。

当前接线：hybrid 在 RRF 后、ACL 复核前，若 retrieval.judge_after_hybrid=true（默认）且 models.judge 已配置，调用 judge 重排 Top 30；未配置 judge 则跳过且不写 degraded。bm25_judge 仍在 BM25 后调用 judge。图中 RRF → Judge 是实线可选边；judge 失败才写 decision_unavailable †5。

auto · PostgreSQL

直接解析为 hybrid，无论 embedding / extractor 是否配置。缺通道按能力裁剪并写 degraded[]：缺 embedding → dense_not_enabled；缺 extractor → event_not_enabled。

auto · SQLite + embedding

先探测 has_embeddings 是否有可见向量：有 → hybrid；无 → index_missing；探测失败 → embedding_unavailable。两种情况都继续检查 extractor / events；配置了 provider 不等于已经有向量。

auto · SQLite 兜底

无可见向量（或未配 embedding）时继续看 extractor / events：有 events → hybrid（event-only；dense 按原因报 index_missing / dense_not_enabled）；否则 → bm25。event 查询失败也回 bm25。

显式 hybrid / event

hybrid 缺通道时裁剪并写 degraded；judge 仅在 judge_after_hybrid=true 且 models.judge 已配置时调用，无 judge 不写 degraded。显式 event 失败回 BM25。

score(d) = Σc wc / (60 + rankc(d)) c ∈ {bm25, dense, event}；同一 chunk 在多个通道出现则累加；只使用名次，不使用原始分数。

k 固定 60。rrf_bm25_weight、rrf_dense_weight、rrf_event_weight 默认都是 1.0；0 合法，但通道仍会执行，只是不贡献分数。

权重不是概率，也不做归一化；它只改变某一路名次的相对贡献。融合后按分数降序、同分按 chunk_id 排序。

# 单通道 rank 1
BM25  #1                   1.0 / 61            = 0.01639
Dense #1                   1.2 / 61            = 0.01967   ← 权重让 dense 头名更高
Event #1                   0.8 / 61            = 0.01311

# 两个通道都出现的文档，累加后通常赢过单通道
BM25  #2 + Dense #2        1.0/62 + 1.2/62     = 0.03548   ← consensus
BM25  #1 + Event #1        1.0/61 + 0.8/61     = 0.02951

04 / ZERO MODEL

零模型也能用the default is a baseline, not a failure mode

四类模型槽位的默认值都是 provider = "none"。没有向量模型、没有 judge、没有 LLM，lkb 仍然能导入、检索、给出带引用的抽取式答案。先把基线跑通，再按瓶颈加模型。

ZERO-MODEL BASELINE

BM25 → 抽取式答案 → 引用

默认路径不依赖任何外部 API，可离线启动。抽取式答案直接选句并附 citations；LLM 不可用只会让 mode 保持 extractive，不会让检索失败。把零模型当成“降级模式”会误判产品基线。

01 / EMBEDDING

向量模型

dense recall
解决什么
同义改写、跨语言、自然语言问句与原文措辞不一致时的语义召回；补 BM25 漏掉的候选。
何时值得加
评测显示 BM25 的漏召回主要来自词汇不匹配；语料以自然语言为主，或需要跨语言检索。solo 配好本地 embedding 且有可见向量后，auto 会自动切 hybrid。
成本 / 延迟
每次查询一次嵌入；索引期为每个 chunk 存向量。solo 的 3 万切片 float32 约 120 MB；目标查询嵌入 ≤ 300 ms。
不加会怎样
dense 通道写 dense_not_enabled；BM25 与抽取式答案继续工作。
02 / JUDGE

判别模型

decision rerank
解决什么
“已经召回，但没排上去”。对 Top 30 候选做证据判断与打分，只改顺序，不找回漏掉的文档。
何时值得加
召回集足够、排序是瓶颈；基准显示 RRF 之后 nDCG 仍有明显空间。hybrid 默认在 judge 已配置时后置重排，不必切到 bm25_judge。
成本 / 延迟
每查询一次模型调用；公开口径 70–500 ms，按部署与网络实测。无需 GPU，但需要可用的 judge 模型。
不加会怎样
hybrid 未配置 judge 会静默跳过，不写 degraded；bm25_judge 未配置才写 decision_unavailable；配置后失败保持原顺序。
03 / LLM

生成模型

answer synthesis
解决什么
多文档归纳、自然语言解释、改写与摘要；不负责召回，也不能替代检索。
何时值得加
用户需要摘要 / 解释而不是原文片段；能接受 token 成本、配额与首 token 延迟。
成本 / 延迟
输入 + 输出 token；team 目标首 token ≤ 1.5 s。失败时回抽取式，不阻塞回答。
不加会怎样
默认抽取式 + 模板；引用仍然完整。llm_unavailable 只在调用失败时出现。
第四个槽位 models.extractor 不是查询时模型。 它在摄入期抽取事件 / 实体，决定 event 通道有没有候选；加它要重索引。没有抽取器时，显式请求 event 会写 event_not_enabled；不请求就不参与。
solo 零模型 → solo + 本地 embedding（auto 自动 hybrid） → team / enterprise + judge / LLM

成本 / 延迟顺序：BM25 < embedding < judge < LLM；extractor 是索引期一次性成本 + 重索引。每次只加一个变量，先复测基线。

05 / NOTES & QUOTA

我的笔记与配额分层My notes · quota layers

我的笔记不是 solo 专属：任何层级（solo / team / enterprise）的每个用户都有自己的私有笔记，仅本人可见。页面 = 笔记，空间 = 笔记本；笔记由系统私有空间承载，不占自助空间配额。配额只治理空间与模型用量。

ANY TIER · MY NOTES

我的笔记 / My notes

私有（仅本人可见）；solo / team / enterprise 都可用。当前入口是 Web Wiki，不是桌面本地 vault。

  • 页面 = 笔记，空间 = 笔记本；正文以 Page / Revision 保存，保存生成新 revision。
  • 检索：保存后进入统一索引，可被搜索 / 问答；没有模型时走抽取式回退。
  • 系统私有空间：每用户一个 notes_* 空间；POST/GET /api/v1/notes/space 幂等确保，ACL 仅本人，管理员读内容 404；不占自助空间配额。已实现
  • 块编辑器：Markdown / Blocks 切换、分块 / 拖拽 / 类型工具栏 / 实时预览；Markdown 是事实源，代码围栏 / 表格不拆。已实现
  • 插件接口 v0：manifest / hooks / block renderer / command registry，编译内置；v0 骨架已实现。v0 骨架远程加载 / 沙箱 / 市场未实现。
  • 入口：顶部栏「新建笔记」/「笔记」；solo / team / enterprise 共用同一套 Page / Revision 与搜索。
privatePage / RevisionWeb / SQLite / PG
QUOTA LAYERS · SOLO / TEAM / ENTERPRISE

配额分层 / Quota layers

我的笔记由系统私有空间承载，不占自助空间配额；配额只治理空间与模型用量。solo 默认只读，team / enterprise 才开放配额管理。

  • solo：features.quotas=false；仅用量可读，配额写接口返回 403 feature_disabled；可显式 opt-in。
  • team / enterprise：features.quotas=true；scope chain tenant → group / user → space；token 配额另支持 tenant / space / user / role。
  • hard / soft：hard 阻断（字节 413、计数 429），soft 不阻断；80% / 95% 告警仍是目标。override 带 reason 与 expires_at。
  • 不是限速：quota 管总量，rate limit 管每秒突发；quota_exceeded / rate_limited / 402 payment_required 不混用。
  • 写入口与审计：空间配额、admin token 配额、override；关闭 flag 不删除已有记录，变更 / override 写审计。

06 / ADMIN

后台设计方向name the style, then change the information architecture

结论先说：现在的问题不是配色，是信息架构。现有 token、表格、空态 / 骨架 / 确认流程都可以保留；需要把“设置表单”改成“资源控制台”。

STYLE VERDICT

Cloud Control Plane · 云控制台风格

企业基础设施控制台，不是 SaaS 营销后台。以资源为中心，服务导航为骨架，表格 + 详情抽屉为主操作面，IAM 策略矩阵表达权限。

参考的是交互模型，不是视觉复制：AWS Console 的服务导航与资源列表、Google Cloud 的 IAM 策略、Azure Portal 的 blade / drawer、Cloudflare 的高密度列表与 scope、Vercel 的克制深色界面。目标读者是管理员和平台工程师，不是营销访客。

为什么现在不像云控制台

基于 web/src/pages/admin/AdminPage.tsx、features/admin/GroupsPanel.tsx、RolesPanel.tsx 的现状。

管理后台现状与目标
现状结果目标
max-w-[900px] 单列 + 11 个平级 tab 没有服务层级，所有管理项同一权重；页面像“设置页”，不像控制面。 56 px 全局顶栏 + 240 px 分组服务导航 + 面包屑 + 内容区。

设计原则

按控制台的信息层级排列，不是按组件库排列。

01

全局顶栏 + 左侧服务导航

顶栏放组织 / 租户切换、环境、全局搜索、帮助、账号；左栏按 Identity / Content / Platform / Governance 分组。不要把 11 个 tab 平铺成唯一导航。

02

面包屑 → 页面头 → 工具栏 → 表格

页面头包含资源名、类型、数量、创建时间与主操作；工具栏放搜索、过滤 chip、列选择、刷新。主操作只有一个，且用绿色。

03

资源表格是主操作面

36 px 行高、sticky header、行 hover、可选中、分页、空态与骨架。表格不是 Card 的附属内容；它承担扫描、比较、批量操作。

04

右侧详情抽屉

480 px 抽屉，URL 可寻址，Esc 关闭；内部再分 Overview / Members / Policies / Audit。选资源不跳页，列表上下文不丢失。

05

IAM 权限矩阵

能力行 × 角色列；scope 选择器；直接授予与继承分开显示；保存前展示 effective diff。权限组页面必须能回答“谁能做什么、在哪、从哪继承”。

06

状态与危险操作

骨架、空态带下一步、错误可重试、degraded 可折叠；危险操作二次确认，要求输入资源名并展示影响范围（成员数、策略数、是否最后一个 Owner）。

07

用现有 token，不发明第二套皮肤

直接使用 --color-canvas/surface/panel/raise/line/fg/fg-2/fg-3/accent；8–10 px 圆角、1 px 边框、150 ms 过渡；阴影只给抽屉，不给每张 Card。

08

先做对，再做“云”

不要用假指标、英雄卡片或装饰性拓扑图撑场面。控制台的专业感来自一致的信息架构、可解释的权限与可靠的状态反馈。
